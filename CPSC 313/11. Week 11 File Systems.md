## Hierarchical Naming
- generalized tree structure

	- lookup is iterative (and potentially expensive) operation

## Directory Representation
- directories are regular files with a special format
- a field in a file's inode indicates that the file is of a type directory
- a directory entry is a pair of name and associated inode number
	- user programs can read directories like files
	- only OS can write DIRS, users can corrupt the structure

## Walking a Dir Path
- given C1/C2/C3
- start at root dir (which is fixed known inumber) if path begins with / or current working directory otherwise

1. let inum = starting inum; current component = next component (c1)
2. read contents of the objects whose inumber is inum (this is a dir)
3. find the entry with the name equal to the current component
4. find the associated inumber

Read the inode for that inumber
- if it's the last component we're done
- if it is not a directory and we have more components, then it's a bad pathname! (can't find it also bad)
- if it is a directory, set the inum to the inumber; and set current component to next part of path and iterate back to step 2

## rm removing a link
- we think of this as removing a file, but it's not quite that
- rm foo removes the name foo and decrements the link count of the inode it references
- inode and file are removed when the link count goes down to 0.

## Symbolic Links
- a file that contains a pathname to another file
	- ln -s target new-alias

- creates a new inode that stores the target pathname as a string
	- does not increment target's link count or do anything with the target inode

- when the OS encounters a symbolic link, it continues pathname processing using the pathname stored in the file
- continuing from the current directory unless the pathname in the symbolic link is an absolute name

**removing symbolic link**
	removes link but doesnt touch file

**removing file that the link points to**
	does nothing to the link, just like a dangling pointer in memory

## Working directories
- using full pathnames is annoying!
- posix maintains a current working directory (cwd) for each process. the OS stores the inumber on behalf of each user process
- if the path's first character is / then the OS begins decoding the path at the root, otherwise it works from the cwd
- a search path is a list of current working directories. this can be searched one after another to try to resolve a name (liek typing ls at the shell!)
