## Per-process data structures

## File System Design Goals and Constraints
- long lived and robust
- - many files created, deleted, extended and truncated over time
- performance should not degrade with time (too much)

- general purpose
	- different file sizes; files can be sparse
	- different access patterns: sequential and arbitrary ("random")

- performance dictated by media hardware
	- rotating disk or ssd
	- file is a collection of disk blocks, storing data + metadata
	- seeking can be much slower than transferring all data
	- where blocks are really matters

## Sparse Files
**Purpose**
- some files represent data placed at particular offsets to a starting point
- potentially with large gaps in between
- rather than a continuous stream of data

**Implementation**
- e.g. write one byte at offset 0 and another at offset $2^{30}-1$
- file size is $2^{30}$
- but storing that data requires only 2 disk blocks for the file's data
	- allocate $2^{30}$ worth of blocks would waste valuable disk space

vm images, executables, modern dbs

**Cons**

- degrades performance of sequential access (reading blocks that may be far away)

## Picking a block size

**Cons**

	- called internal fragmentation
- particularly problematic for small files
	- and most files are small lmfao
