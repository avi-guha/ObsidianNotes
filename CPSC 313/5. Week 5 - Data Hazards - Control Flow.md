## Control Flow Hazards
- what happens if the next instruction we have has the PC of the next instruction we actually want to execute
- we don't want our state machine to be overwritten by instructions in the pipeline that aren't meant to be running!
- we have the information we need during the fetch cycle (so that when we get to the next cycle, we can latch the valC into the fetch register)

unconditional jumps don't introduce a stall!
same with calls (we know the route we're going to take!)

what about ret?
- some stalling for sure.
- need to read from memory

### Conditional Jump instructions
- either valP or valC but we don't know which one to take!
- we figure it out during execute (from cond! combining the ifun and cond)
- we can make a guess
- it's remarkably predictable!

## Branch Prediction
- we use the prediction, we assume the prediction is right, and if it's wrong then we go back to fix it

## Branch Prediction Algorithms
- Always taken: assume valC is nextPC
- Never taken: assume valP is nextPC
- or fancier things, but how should we decide which is correct?

let's try

#### Always Taken
- yes.

#### Never Taken
- yes.

We only find out we mis-predict after the execute stage. we need to go back! but how? 
- we need to keep valP around until the execute stage (if we mis-predict and find out in the execution stage, we can discard the work we've done and instead feed in valP, or valC (vice-versa))


```asm
andq %rbp, %rbp
je error

error:
irmovq 0xFFFFFFFFFFFFFFFF, %rax
ret
```
- backward jumps are often used to repeat a loop body, so usually taken
- forward jumps are typically conditionals, and may or may not be taken

## Our pipeline is very simplified
- not all alu operations take a single cycle
- division is particularly difficult
- there can be multiple functional uints
	- more than one adder/multiplier/divider/whatever
	- super scalar architectures
		- issue more than one instruction per cycle
- out of order execution and other tricks
	- we can reodrer instructions to execute faster
	- move memory reads earlier or dependent instructions later
	- renaming registers on the fly to avoid "output" dependencies

- memory accesses can take many clock cycles; not all accesses take the same time

## What does a real intel execution unit look like
execution:
- multiple instructions fetched at once
- instructions can be reordered; registers can be renamed to avoid name conflicts
- instructions wait in the scheduler (also called reservation station) until operands are ready
- sent thorugh one of multiple execution units

## Other kinds of parallelism
Multitasking (multiprogramming)
- basically an illusion
- software make it looks like many things are happening at once but the OS just rapidly switches between different jobs

Multiprocessing:
- place multiple processing units (CPUs) on a machine so you can run different programs on each unit

Parallel runtimes:
- leverage multiprocessing or other forms of parallelism
	- the parallelism can be figured out either manually or automatically
	- need a runtiem system to dispatch different tasks to different processing elements
- multithreading:
	- again idea is to allow different threads to run on different processing units
	- but can still have multiple software threads that run on single HW core

## Thread level parallelism
- programmers express this explicitly
	- requires software api or language support
	- threads or other things
- granularity
	- coarse grain, limited by fixed overhead (create, schedule)
- exploited by 
	- multi core processors
		- and maybe multichip (less common)
	- also asynchronous communication with other devices

## Hyper Threading
- memory latency is a problem
- fast hardware implemented, thread switch while waiting for memory
	- similar to software thread waiting for disk read
- each has N hyper threads (usually 2)
	- implemented by having N copies of all registers
	- exploited by virtual cores (# of cores, # of hyperthreads)
