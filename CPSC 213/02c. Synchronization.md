## The importance of Mutual Exclusion
- Shared Data
	- data structure that could be accessed by multiple threads
	- typically concurrent access to shared data is a bug
- Critical Sections
	- sections that access shared data
- Race Condition
	- simultaneous access to critical section by multiple threads (at least one updating the shared data)
	- conflicting operations on shared data are arbitrarily interleaved
	- unpredictable (non-deterministic) program behaviour (a serious bug most of the time)
- Mutual Exclusion
	- a mechanism implemented in software (with hardware support)
	- to ensure *mutual exclusion*, they are executed by one thread at a time
	- reading and waiting should be handled differently (we'll talk about this later)

## Mutual Exclusion Using Locks
- Lock semantics
	- lock is either held by a thread or available
- at most one thread can hold a lock at a time
- a thread attempting to acquire a lock that is already held will be forced to wait
- primitive operations:
	- lock: (acquire lock, wait if necessary)
	- unlock: release lock, if another thread is waiting allow it to run

### Atomic Memory Exchange Instructions
- we need a new Assembly instruction
	- read AND write in a single instruction 
	- no intervening access from other threads
- atomicity: operations are performed in single, indivisible unit
- atomic memory exchange:
	- one type of atomic instruction (some ISAs implement other types)
	- group a load and store together atomically
	- exchange value of register and memory location
![[Pasted image 20241119132007.png]]

- can't be done in the CPU alone
	- must be able to synchronize across multiple cores and CPUS
	- multiple cores accessing same location in memroy at the same time
- part of this shit is implemented *in the memory bus*
	- memory bus synchronizes every CPU's access to memory
	- bus couples both parts of exchange (read and write)
	- bus ensures no other transaction intervenes
	- higher overhead (slower than normal load and store instructions), done in the bus not CPU

#### Are spinlocks worth it?
- spinlocks are necessary and fine if the spinner only waits for a short time
- spinlocks waste CPU cycles (polling)
	- cpu busy waiting for a thread that may take a long time to run
	- if running a single CPU, other threads simply can't progress
		- WAIT for a long time LMAO
		- pre-empt a thread, check spin lock, runs for its quantum, gets pre-empted finally unlocks, then finally other thread can own the lock

#### Blocking Locks
- idea: block threads when they CANNOT run.
	- a thread waiting for an event should block so that other threads may run first
	- should be unblocked when the event happens
- blocking locks for mutual exclusion
	- attempting to acquire a held lock blocks calling thread
	- *blocked threads TCB stored in lock's waiting queue* (more on this later...)
	- releasing a lock unblocks first thread in waiting queue
		- removes it from waiting queue, adds it to ready queue
- blocking locks for event notification
	- wait for event by blocking (waiting queue for event)
	- event signal unblocks and moves thread from queue to ready queue

We use queues for locks!! how neat!
- we need multiple waiting queues so that we don't unblock threads from joins

### Spinlocks vs Blocking Locks
- Spinlocks have low overhead when uncontended (no other threads compete for this lock)
	- waiting for lock has high overhead and wastes resources
	- used for short expected waits with minimal contention
	- used in implementation of blocking locks (**HUH**)
- Blokcing Locks:
	- lock has FIXED overhead
	- if uncontended, overhead is higher than spinlocks
	- but if contended then theres less waste of CPU resources on spinning
	- used when lock may be held for long time, or with high contention

"*blocked threads TCB stored in lock's waiting queue*"
- The waiting queue is shared data.
- we protect it with a spin lock

### Mutex (monitors) and Condition Variables
- Mutual exclusion and inter-thread synchronization (let threads send and receive messages between each other)
	- introduced by some big fucking thinkers
	- basis for synchronization primitives in Unix, Java, etc
- Monitor (mutex)
	- blocking lock to guarantee mutual exclusion
	- basic operations: lock and unlock (enter and exit)
- Condition Variable
	- allow threads to synchronize events with each other
	- wait: blocks until another thread signals
	- signal: unblocks a thread currently waiting
	- associated to a mutex, must have a mutex lock held

#### Using Conditions
- basic formulation:
	- one thread acquires mutex and may wait for a condition to be established

```C

while(!desiredState)
	wait(cond)

doSomethingUesful();
unlock(mutex)
```
- another thread acquires mutex, establishes condition and signals waiter, if there is one

```C

desiredState = 1;
signal(cond);
unlock(mutex);
```

### Problems with Conditions
- signal "awakens" at most one thread
	- waiting thread cannot continue until signaler releases the mutex explicitly
	- a third thread could intervene and acquire mutex before waiter
	- waiter must thus re-check the wait condition
	- if no threads are waiting then calling the signal has no effect
	- why we use while(!desiredState) instead of if(!desiredState)

## Beer Example
- Beer pitcher is a shared data structure with associated operations
	- operation pour(): reduces beer left by 1
	- refill(): adds more beer to pitcher (beer left increased by N)
- implementation goal
	- synchronize access to the pitcher
	- pouring from empty pitcher require waiting for it to be refilled
	- filling pitcher releases waiting threads
- use
	- glasses = # of glasses of beer left in pitcher
	- mx = mutex
	- hasBeer = cond indicating there's at least one glass of beer

```C
struct BeerPitcher {
	int glasses;
	uthread_mutex_t mx;
	uthread_cond_t hasBeer;
}

struct BeerPitcher* createAndInitializePitcher() {
	struct BeerPitcher *p = malloc(sizeof(struct BeerPitcher));
	p->glasses = 0; // doesn't matter what it's initialized to
	p->mx = uthread_mutex_create();
	p->hasBeer = uthread_cond_create(p->mx);
}

void pour(struct BeerPitcher* p) {
	uthread_mutex_lock(p->mx);
	while(p->glasses == 0)
		uthread_cond_wait(p->hasBeer);

	p->glasses--;
	uthread_mutex_unlock(p->mx);
}

void refill(struct BeerPithcer *p, int n) {
	uthread_mutex_lock(p->mx);
	p->glasses += n;
	for (int i = 0; i < n; i++) { // more cost, but only wake up threads that won't have to wait
		uthread_cond_signal(p->hasBeer); // dequeues one thread
	}
	uthread_mutex_unlock(p->mx);
}

void refill(struct BeerPithcer *p, int n) {
	uthread_mutex_lock(p->mx);
	p->glasses += n;
	uthread_cond_broadcast(p->hasBeer); // broadcast is advantageous since we pop entire queue
	// in the case that there aren't significantly more people than in n, then only a few threads will be left waiting when p->glasses = 0
	// do we just assume its O(1)? maybe...
	uthread_mutex_unlock(p->mx);
}
```

### Beer Implementation: Automatic Refill
- what if you want to refill automatically?
	- suppose the pitcher has capacity max glasses
	- pouring removes one glass if there is enough beer and waits otherwise
	- refilling loops forever waiting for the pitcher to be empty
		- when empty, refill it to capacity and wake up any waiting threads

Setup
```C
struct BeerPitcher {
	int glasses;
	int maxGlasses;
	uthread_mutex_t mx;
	uthread_cond_t hasBeer;
	uthread_cond_t isEmpty;
}

struct BeerPitcher* createAndInitializePitcher() {
	struct BeerPitcher *p = malloc(sizeof(struct BeerPitcher));
	p->glasses = 0;
	p->maxGlasses = n;
	p->mx = uthread_mutex_create();
	p->hasBeer = uthread_cond_create(p->mx);
	p->isEmpty = uthread_cond_create(p->mx);
}

// updated implementation!

void pour(struct BeerPitcher *p) {  
	uthread_mutex_lock(p->mx);  
	while (p->glasses == 0)  // check to pour
		uthread_cond_wait(p->hasBeer);
		  
	p->glasses--;  
	if (p->glasses == 0)   // check to signal bartender
		uthread_cond_signal(p->isEmpty);  
		
	uthread_mutex_unlock(p->mx);  
}

void refill(struct BeerPitcher *p) {  
	uthread_mutex_lock(p->mx);  
	
	while (1) {  
		while (p->glasses > 0)  // could actually be an if statement!
			uthread_cond_wait(p->isEmpty); // if there were multiple bar tenders we need to wait
		
		p->glasses += p->maxGlasses;
		for (int i=0; i < p->maxGlasses; i++)  // could also broadcast
			uthread_cond_signal(p->hasBeer);  
	}
	  
	uthread_mutex_unlock(p->mx);  
}
```

## Reader-Writer Monitors
- critical sections could be classified as:
	- readers: only read shared data, do not modify it
	- writers: update shared data
- we could then weaken mutual exclusion constraint
	- writers require exclusive access (mutual exclusion wowowow)
	- multiple readers can access the monitor concurrently
- reader-writer monitors
	- can be free, *held for reading* or *held for writing*
	- if held for reading, multiple readers can access simultaneously!!!!
	- **three states**

### Operations on Reader-Writer Monitors
**mutex_lock()**: lock for writing
- only acquires lock if free
- sets state to held for writing
**mutex_lock_read_only()**:
- if lock is free, set its state to held for reading
- increments reader count (or a set)
	- similar to ref count!
**mutex_unlock()**:
- if held for writing, set state to free
- if held for reading: decrement reader count
	- set state to free if count is zero (or set is empty)


### Fair Access to Reader-Writer Lock (it depends!)
Question: writer thread is waiting for reader count to hit zero, but do we want more reader threads to be able to access our data?
- depends! if we let readers keep being added, then they'll run concurrently (its faster)
	- but our writer may end up waiting a long time to get access
- otherwise the data will be outdated, and in some cases we want to update information as soon as possible

Disallowing new readers while writer is waiting:
- affects thread that could be running and isn't
- provides fair access to monitor

## Semaphores: Dijkstra! AGAIN!
- #1 async hater
- semaphore is a non-negative **atomic** counter (aka indivisible)
	- attempting to make the counter negative blocks the calling thread
	- no operation to read the counter value, only to change it
- P(s) (*wait(s)*, dec(s), sub(s,n)):
	- tries to reduce s
	- atomic: blocks until s > 0, then decrements s
- V(s) (or *signals*, incs, add(s,n))
	- increases s
	- atomic: increases s and unblocks waiting threads if necessary

### Ordering threads using semaphores
- if thread B must wait for thread A to finish
	- initialize semaphore b to 0
	- A: thread_sem_signal(b);
	- B: thread_sem_wait(b);

if both threads need to wait for each other
- initialize two semaphores and b with 0
- thread A signals(a)
- waits on b
- thread b signals b
- and waits on a

all of the options will work, as long as any of the threads begins with a **signal(..)**
- in case that both threads wait first, then we end up in deadlock since the signal will never be called

## Avoiding Deadlocks
- if you don't need them, don't use multiple threads
- if you don't need them, don't use shared variables
	- use locals and params if possible!
- avoid unnecessary locks
	- when possible use atomic data structures and lock-free synchronization
	- if possible use only one lock at a time
		- deadlock often happens if a lock that holds a lock waits for another lock
- evaluate the scope of the lock
	- could be avoided by reducing portion of code that needs locks

- organize locks into precedence hierarchy
	- each lock is assigned to a unique precedence number
	- before thread X acquires lock i, it must hold all higher precedence locks (must get them in this order)
	- ensures that any thread holding lock i cannot be waiting for X
		- locks are always acquired in the same order

**options but not discussed**
- limit wait time on locks
	- provide alternate action if it doesnt work
- detect and destroy
	- if you can't avoid a deadlock, detect when its occured
	- and break deadlock by interrupting/terminating threads
