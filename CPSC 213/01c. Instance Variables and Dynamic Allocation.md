## Struct Size and Alignment
- alignment rules apply inside of a struct
	- each instance variable will be aligned according to it's type size
	- structs are usually aligned according to their largest member variable type
- structs can mix types (padding might be added in or after the members)
	- padding is based on alignment within a struct, which corresponds to the largest type
```C
struct X {
	char a;
	char b; // ..2 bytes (a b - - i i i i )
	int i; // 4 bytes, will start at 4, 2 unallocated bytes
} // alignment = 4 bytes (largest primitive within the struct)
  // size = 8 bytes

struct Y {
	char a; // 0 (a - - -)
	int i;  // 4 (i i i i)
	char b; // 8 (b - - -)
} // alignment = 4
  // size = TWELVE (12) bytes
```

tl;dr the way you order structs can change how wasteful you are of memory

### What Malloc and Free do
- Organization of memory
	- statically allocated: code, static data
	- the rest is unused or dynamically allocated
- Malloc/free
	- implemented in library
	- manage a chunk of memory called the Heap
	- keep track of what's allocated or free
- malloc
	- find a free chunk of memory of appropriate size
	- mark it allocated
	- return pointer to it
- free
	- use pointer to determine allocated size
	- mark referenced memory as free

### Issues with Explicit Deallocation
- what free(x) does
	- deallocated chunk of memory starting at address x
	- this memory can be reused by subsequent calls to malloc
	- (you can't deallocate a chunk of memory by starting in the middle of something allocated)
- what free(x) doesn't do
	- change what x points to
	- change other pointers pointing to that memory
	- does not change/"erase" data in freed memory (can simply be allocated in the future)

Pointer to an object that is not allocated for the purpose it's been called for
- often caused by use-after-free
- could point to unallocated memory (best case scenario most of the times...)
- if malloc has been called since last free, could point to another object
- also happens with incorrect pointer manipulation
Why is this a problem
- program thinks it's writing to one object, but may be writing to another
- program may be writing to object of another type (looool)
- if memory got reallocated, u could mess around and create unintended consequences

### Reference Counting
- can use reference counting to track object use
	- initialize the reference count to 1 (the caller has a reference)
	- any procedure that stores a reference starts using the object must increemnt
	- any procedure that discards a reference (or stops using the object) can decrement the count
	- never call free directly
		- object itself will be freed when count goes to zero
