## I/O Controller Communication
- I/O Mapped memory 
	- addresses beyond end of main memory (ie beyond 0x8000000)
	- ranges assigned to each controller
	- usually configured at boot time (assigned)
	- loads/stores are translated into I/O bus messages in the system
- Programmed I/O (PIO)
	- CPU transfers word at a time to/from the IO Controller
	- standard load/store instructions to IO mapped-memory
	- i.e. this allows the cpu to communicate not just with the memory but also with the controller

## PIO Limitations - Solutions
reading/writing large amounts of data slows us the fuck down
- we can only transfer one word at a time
- our device is much slower than the CPU
IO controller cannot initiate communication **under the PIO** (PIO gets initiated by CPU)
- sometimes CPU asks for data
- sometimes controller should receive data for the CPU
- We must request data, but it might not be available!
- polling (do you have data for me? do you have data for me? - *prevents the cpu from doing anything else when it polls*)

### Polling Example
CPU
```C
int pollDeviceForValue() {
	volatile int* ready = 0x80000100
	volatile int* value = 0x80000104

	while(!*ready) {}
	return *value;
}

void send(int v) {
	volatile int* ready = 0x80000100;
	volatile int* value = 0x80000104
	*value = v;
	*ready = 1;
}
```
- volatile means that you check the value everytime you see this, don't assume its the same otherwise (compiler optimization without it would result in a polling function that never returns...)

## Autonomous Controller Operation
**Direct Memory Access (DMA like the cheats!!!)**
- controller can send/read data from/to any main memory address
- CPU is oblivious to these transfers
- DMA addresses and sizes are programmed by CPU using PIO
	- *"CPU: hey controller, write some data to memory at this address"*
	- CPU sends and forgets

**CPU Interrupts**
- controller can signal the CPU when needed
- CPU will check for interrupts on every cycle
	- very fast, clock-speed poll (we just check if its changed or no and carry on)
- CPU jumps to controllers' *interrupt service routine* if it is interrupting

#### Implementing Interrupts in a Simple CPU
- new special-purpose CPU registers
	- *isDeviceInterrupting* set by IO controller to signal interrupt
	- *interruptControllerID* set by IO controller to identify device
	- *interruptVectorBase* interrupt-handler **jump table** (based on input wtf do i do about it), initialized at boot time
- modified fetch-execute cycle
```C
while (true) {
	if (isDeviceInterrupting) {
		r[5] <- r[5] - 4; m[r[5]] <- r[6]; r[6] <- PC // store our return address
		PC <- interruptVectorBase[interruptControllerID]; // call our interrupt service routine
	}
	fetch();
	execute();
}

RTI (return from interrupt instruction)
t ← r[6]; r[6] ← m[r[5]]; r[5] ← r[5] + 4;  // load from saved memory (and dealloc the space)
isDeviceInterrupting ← 0; PC ← t;
```

## Making Code Asynchronous
- we can separate the code parts and run them separately (taking from example to read from the disk)
1. Request something
```C
char buf[numBytes];
diskRead(buf, blockNum, numBytes)
```

2. handle data once reqeust is completed

### Writing Async in C
**Events**
- things that cause asynchronous code to run (disk read completion)
**Event Handler**
- code that runs when event occurs (code that computes checksum)

Handlers are registered to a specific event, events are fired to trigger the execution of the handler!

In Code:
- request and handler registration are listed together in the code (waooow function pointer)
- this code continues; it does not wait for the event (interrupt)
- handler runs asynchronously when event occurs

```C
void computeChecksum(char *buf, int blockNum, int numBytes) {
	char xsum = 0;
	for (int i = 0; i < numBytes; i++)
		xsum ^= buf[i];
}

void checksumDiskData(int blockNum, int numBytes) {
	char buf[numBytes]; // dangling pointer, worry aobut it later
	diskRead(buf, blockNum, numBytes, computeChecksum);
}
```

## Disk Read (Simplified, with PIO and Interrupts)
- The PIO message sent to disk has several fields
	- each field has a different device memory address
	- accessed like a struct
- writes are to device memory (write it to read!)
	- messages across bus to IO controller; not writes to main memory
	- addresses can be accessed kinda like a struct
		- just remember these addresses are actually mapped to IO, and nto actually part of main memory

```C
int* diskAddress = (int*) 0x80001000

#DEFINE DISK_OP_READ 1
#DEFINE DISK_OP_WRITE 2

struct disk_ctl {
	int op; // read/write
	char* buf; // address for data
	int blockNum; // disk block
	int numBytes; // how much data
}

void diskRead(char* buf, int blockNum, int numBytes, 
			  void (*whenComplete) (char*, int, int) // handler is put on a queue (function pointer, runs it when interrupt happens or something)
			  ) {
	struct disk_ctl* dc = (struct disk_ctl*) diskAddress;
	enqueue_handler (whenComplete, buf, blockNum, numBytes);
	dc->op = DISK_OP_READ; // maybe write last, simplified like a flag
	dc->buf = buf;
	dc->blockNum = blockNum;
	dc->numBytes = numBytes;
}
```

### PIO Reads from the IO side
- InterruptVector, DeviceID, and PIO address
	- initialized at compile time by OS when device connects
```C
#define MAX_DEVICES 16
void (*interruptVector [MAX_DEVICES])();

int diskID = 4;
interruptVector [diskID] = diskISR; // this is the interrupt service routine address!


/* ENQUEUED ON PREVIOUS SLIDE ABOVE */
struct handler_dsc { // package for the handler
	void (*handler) (char*, int, int); // give ya handler
	char *buf; // give ya arguments
	int blockNum; // params for the handler
	int numBytes; // who knew
};


void diskISR() {
	struct handler_dsc hd;
	dequeue_handler (&hd);
	hd.handler (hd.buf, hd.blockNum, hd.numBytes);
}

```
- interrupt handler
	- find event handler and fire event
	- fire means call the procedure, using parameters from our struct

### The issue with devs
- humans like synchrony
	- want each step of a program to complete before the next one starts
	- we use the result of previous steps as input to subsequent steps
- computer systems are asynchronous
	- disk controller takes 10-20 milliseconds
		- CPU can literally execute million instructions
		- we have to let it work
	- many devices send unsolicited data at unpredictable times
		- network packets, mouse clicks, keyboard key presses!
- asynchronous code sad
