## Polymorphism (revisited)
- invoking a method on an object in Java
	- variable that stores the object has a static (apparent) type
	- reference is dynamic, with the dynamic (actual) type
	- object's actual type must be a subtype of the apparent type of the referring variable
	- object's actual type may override methods from the apparent type!
- Polymorphic dispatch
	- target method address (destination of the jump) depends on the actual type of the referenced object
	- call can invoke different methods at different times

#### Polymorphic Dispatch
- method address is determined dynamically
	- compiler cannot hardcode target address in procedure call (*need to know what implementation that we're going to use*)
	- lookup of procedure address happens in runtime
	- address is obtained from memory
- class jump table
	- every class is represented by a class object (only one per class!)
	- instances of the class store a pointer to their class object (actual type)
	  class object stores the class's jump table
	  jump table stores the address of methods implemented by the class
	  address of jump table is determined dynamically
		- we don't know the specific jump table an object will point to, but we will know the offset in the jump table that we will be need to call
	  method's offset into jump table is determined statically

## Implementing a polymorphism in C
- we don't have hidden arguments for this
```C
struct A_class {
	void (*ping) (void *);
	void (*pong) (void *);
};

void A_ping (void *this) {...}
void A_pong (void *this) {...}

struct A_class A_class_obj = {A_ping, A_pong};
```

static object, and now every object we create will point to this jump table

Creating instances of the class
```C
struct A {
	struct A_class *class;  // pointer to the class object
	// instance variables
}

struct A *new_A() { // since we are being sentimental for constructors
	struct A *obj = malloc(sizeof(struct A)); // malloc the size
	obj->class = &A_class_obj; // make it point to the class object
	return obj;
}
```

Object use!
- struct A \*a = new_A();

Calling instance methods
- a->class->ping(a); (*WHAT THE DOT OPERATOR ACTUALLY DOES FOR a.ping()*)
- a->class->pong(a);

## Switch Statements
- semantics the same as sequence of if/else if statements
	- condition of each 'if' tests the same vaiable
- assembly implementation: sequence of branches?
```C
switch (i) {  
	case 0: j = 10; break;  
	case 1: j = 11; break;  
	case 2: j = 12; break;  
	case 3: j = 13; break;  
	default: j = 14; break;  
}
```
do we wanna actually write ts. (beq ... BR L2, beq... BR L3)
- switch statements model a common idiom
	- choosing the result of one computation from a set of options
- switch statements have interesting restrictions
	- case labels must be static, cardinal values (aka numbers)
		- i.e. integers, characters, but NOT strings...*
		- characters are represented by numbers anyways. (*ASCII...*)
	- case labels must be compared for equality to a single expression
\* java actually does allow strings in case.

What are we actually doing in a case (e.g. case 0: means i\==0)
- note that each label represents a code starting line
- so each case value could represent a jump
- break is explicit, so jump out will be handled separately
- we can implement this with an array of jump addresses!
	- call this a jump table!
	- array position represented by case value
	- jump based on array element
	- special case for default outside the range of array.

Computation can be more efficient!!! O(1) array look up with some overhead vs. O(n)
![[Pasted image 20241031133333.png]]
- write out switch statements.... compiler will deal with this for us
- \*jt\[4] will contain our array of cases {case 0, case 1, ....}
- if we fall outside the range of our array we goto default, or we will actually goto the label specified by our array

### Problems with jump table approach
- jump tables have limitations
- you need addresses for all values, which wastes memory...
What if cases start at large values!
Negative cases?? 

### Our Approach (based on case... haha)
- if our labels are sparse or very few cases, just use nested ifs
- otherwise, just use a damn jump table (and waste some space)
Jump table implementation
- Build jump table for all label values between lowest and highest, the gaps will hvae the goto default
- which will goto default if condition is outside range
- normalize condition value to lowest case label (we'll just subtract this value from all of our cases when we index our array)
- and then we use the jump table to directly go to the selected case arm
